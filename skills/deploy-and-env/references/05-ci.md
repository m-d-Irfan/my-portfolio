# CI

The gates, and which ones cannot be skipped.

## The pipeline

```
lint → test → security → budget → build → deploy
```

Fail fast: lint takes seconds and catches the cheapest class of problem. The
security suite runs before the build, because there is no point building an
artifact you will not ship.

## Non-skippable

Three gates have no `continue-on-error`, no `|| true`, and no "just this once":

1. **The security regression suite** (`testing-harness/assets/test_security_regressions.py`).
   One test per audit finding. It exists because S1, S2, S5, S6 and S8 were all
   live in production simultaneously and nothing noticed.
2. **The secret scan.** A committed credential is compromised the moment it is
   pushed; catching it in review is already too late.
3. **`makemigrations --check`.** A model changed without a migration passes
   every local test (SQLite is recreated from models) and fails on the first
   production request.

Everything else can be a warning while it is being adopted. These three cannot,
because each one's failure mode is silent in every other check.

## GitHub Actions

Copy [`assets/ci.yml`](../assets/ci.yml) to `.github/workflows/ci.yml`. The
shape:

```yaml
on:
  push: { branches: [main] }
  pull_request:

jobs:
  backend:    # ruff → pytest → security suite → check --deploy → migrations check
  frontend:   # eslint → vitest → build → budget
  secrets:    # gitleaks over the full history
  deploy:     # only on main, only if all three passed
```

Jobs run in parallel; `deploy` declares `needs: [backend, frontend, secrets]`,
so a red anything blocks the deploy without anyone having to remember.

Notes on the details that matter:

- **A real MySQL service container**, not SQLite. This project runs MySQL in
  production, and the differences are real: case-sensitive table names,
  767-byte index limits on older versions, different transaction semantics
  around DDL. A suite that only ever ran on SQLite has not tested production.
- **`pip install -r requirements.txt`**, not a hand-listed set. If the file is
  incomplete, CI should fail — that is the same failure the server will have.
- **`npm ci`**, not `npm install`. `ci` respects the lockfile exactly.
- **Cache `~/.cache/pip` and `~/.npm`**, keyed on the lockfile hash.
- **`--exit-code 1` on gitleaks.** Without it, findings are printed and the job
  passes.

## The secret scan

```yaml
- name: Scan for secrets
  uses: gitleaks/gitleaks-action@v2
  env:
    GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

Scan **history**, not just the diff. A secret three commits back is as
compromised as one in this PR, and a repo adopting the scan late needs to know
what is already there.

Locally, the same rule enforced earlier — copy
[`assets/.pre-commit-config.yaml`](../assets/.pre-commit-config.yaml):

```bash
pip install pre-commit && pre-commit install
pre-commit run --all-files       # scan the current tree once
```

`check-added-large-files` in that config is not incidental: it is what stops
the next tracked `db.sqlite3` (600 KB of real customer rows and password
hashes) and the next 6.6 MB PNG.

## Budgets in CI

```yaml
- run: npm ci && npm run build
- run: bash scripts/check_budget.sh          # performance-budget
- run: pytest tests/test_query_budget.py     # query counts, payload size
```

`performance-budget` owns the numbers. CI owns that they are enforced rather
than aspired to. **P3** — a 6.6 MB PNG — shipped because nothing checked, not
because anyone decided to.

## Secrets in CI

Repository secrets, never in the workflow file. Referenced as
`${{ secrets.NAME }}`.

- **A secret is not exposed to a fork's pull request.** That is deliberate and
  correct. A workflow needing secrets runs on `push` to `main`, not on
  `pull_request` from a fork.
- **Never `echo` a secret**, even to debug. GitHub masks exact matches in logs
  but not transformations — base64-encoding it defeats the mask entirely.
- **Deploy via SSH key or a deploy token**, scoped to that one repo. Not a
  personal access token with full account access.
- Rotate CI secrets on the same schedule as production, using the same runbook
  (`security-hardening/04-secrets.md`).

## Deploy from CI

```yaml
deploy:
  needs: [backend, frontend, secrets]
  if: github.ref == 'refs/heads/main' && github.event_name == 'push'
  steps:
    - uses: appleboy/ssh-action@v1
      with:
        host: ${{ secrets.DEPLOY_HOST }}
        username: ${{ secrets.DEPLOY_USER }}
        key: ${{ secrets.DEPLOY_SSH_KEY }}
        script: cd ~/daf_backend && bash scripts/deploy.sh
```

The script on the server is the one in
[04-release.md](04-release.md) — `set -euo pipefail`, backup first, health check
last, non-zero exit on failure so the CI job goes red.

A deploy that "succeeded" while the health check failed is worse than a failed
deploy, because nobody looks.

## What CI cannot check

State this plainly rather than implying coverage:

- **That the production `.env` is complete.** CI runs against its own
  environment. The `env -u SECRET_KEY python manage.py check` test proves the
  *mechanism* works; only the server proves the *values* are there. Run
  `check --deploy` on the server as part of the deploy script.
- **That third-party credentials are valid.** A rotated-and-not-deployed
  Steadfast key passes every test and fails on the first real dispatch. That is
  what the post-deploy smoke test in [04](04-release.md) is for.
- **That the migration is safe on production-sized data.** A migration over 40
  rows in CI says nothing about the same migration over 400,000 with a lock
  held.

## Verification

```bash
# 1. The workflow parses.
npx --yes @action-validator/cli .github/workflows/ci.yml

# 2. Everything CI runs, runs locally.
ruff check . && pytest -q
cd "daf front/daf frontend" && npm ci && npm run lint && npm test -- --run && npm run build

# 3. The gates actually fail.
#    Temporarily break one thing and confirm the job goes red:
#    - remove a permission_classes line   → security suite fails
#    - add a fake key to a tracked file   → gitleaks fails
#    - change a model without migrating   → makemigrations --check fails
#    Revert all three afterwards.

# 4. No skipped gates.
grep -n "continue-on-error\|allow_failure\||| true" .github/workflows/ci.yml
# PASS: no output

# 5. Pre-commit is installed locally.
pre-commit run --all-files
# PASS: green
```

Check 3 is the one that matters and the one nobody does. A gate that has never
failed is a gate you have no reason to believe in — the same argument
`testing-harness` makes about regression tests.
